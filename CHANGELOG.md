# Changelog

## Unreleased

- New: guest mode kept local, and new worktrees ([#71](https://github.com/davidelarocca/swift-harness/issues/71), [#105](https://github.com/davidelarocca/swift-harness/issues/105)). `setup-guest.sh` gains three options:
  - `--local` keeps the two files out of the repository, through `.git/info/exclude`, which every worktree shares. Neither git nor other agents see them.
  - `--from <checkout>` gives a new worktree the same two files.
  - `--docs-observe` runs the project's docs check without ever blocking (`docs.blocking: false`).
  - `--ui-isolation <argument>` declares the launch arguments that keep UI tests off the user's real data (`uiTests.isolation`).

  A dry run on a clone of a real app went through every step: audit, timing, guest setup with `--local`, approval, and a real Claude session. The build took 38 s cold and 1 s warm, the tests about 4 minutes, so the build became the fast command. The end-of-turn check passed, the project's own docs check ran in observation, and `git status` showed only Claude's edit. `doctor` named what is left to the user: reviewing the security baseline.
- New: timed commands, opt-in tests left out, unstable tests named ([#104](https://github.com/davidelarocca/swift-harness/issues/104) timing step, [#108](https://github.com/davidelarocca/swift-harness/issues/108)).
  - **Timing:** `scripts/time-commands.sh` times the candidate verify commands. It runs the project's code, so the setup skill asks the user first. Each command runs twice by default (cold, then warm), with its runs, median, worst time and exit codes. The script proposes the fast/full split under the end-of-turn budget (120 s): fast takes the commands in order while their worst times fit. A failing command is left out and named. The script writes nothing itself.
  - **Opt-in tests:** the adoption audit lists the test files that read environment variables, tests that run only when one is set (hardware, live services), to keep them out of the fast command. On a real app it found 33 such files.
  - **Unstable tests:** with `verify.retryFailed`, a failing verify command runs once more. A pass on the rerun is recorded as unstable, in the evidence (with the tests that failed the first time) and in the catch log (kind `unstable`, counted by the report). It does not block. A failure on both runs blocks as before. `setup-guest.sh --retry-failed` sets it.
- New: one engine for every agent ([#106](https://github.com/davidelarocca/swift-harness/issues/106)). `scripts/check.sh` runs the end-of-turn check from a shell, a git hook or another agent such as Codex. It uses the same approval, the same evidence record and catch log, and the same rule of not re-running code that passed or failed before. Its session is named after the agent (`--agent`). `--json` gives the record and the exit code:
  - 0: the verify command passed on this code;
  - 1: a check failed, with the failure output;
  - 3: the verify command did not run, not approved or turned off.

  It finds the plugin data folder the hooks use: `CLAUDE_PLUGIN_DATA`, else the only `swift-harness-*` folder, else the one that holds this project's approval. The scope contract is reported as information. The README gives a git `pre-commit` recipe (tested: a failing check stops the commit, a fixed one goes through) and a line for another agent's rules.
- New: in guest mode the project's own rules are protected ([#109](https://github.com/davidelarocca/swift-harness/issues/109)). `setup-guest.sh` adds the agent rules that exist (`CLAUDE.md`, `.claude/CLAUDE.md`, `AGENTS.md`, `.claude/rules/`) to `protectedPaths`, so the guard asks before Claude edits them, and an edit through the shell is reported at the end of the turn. `--owned <path>` adds docs the project lets only some people edit. A path that does not exist is left out, with a message. A project without those files gets none. Remove any of them from the config to lift it.
- New: the project's own docs check as an adapter ([#105](https://github.com/davidelarocca/swift-harness/issues/105), v0). `docs.command` names it, and it runs instead of the harness's docs check.
  - **Approval:** it is part of the verify approval (the command and the files it names), since it is the project's code. Not approved, it does not run, and the record and the user say so.
  - **When it runs:** at session start, its problems already there are taken as the start. At the end of a turn when the docs changed (this does not re-run the build), new problems block once with the project's own output; the same problems do not block twice.
  - **Exit codes:** an exit other than 0 or 1 means it could not run, so it is *not checked*, with the reason, never taken for known problems.
  - **Records:** its result, with its duration, is in the turn's evidence record. Blocks, fixes and failures left unfixed are in the catch log.
  - **Observation:** `docs.blocking: false` records it without ever blocking (catch log kind `observed`), the base for measuring the start-in-observation hypothesis.
  - **Elsewhere:** `check-sensitivity --verify` credits it for the docs operator. The adoption audit proposes it instead of `--no-docs`, and `setup-guest.sh` takes `--docs-command`. `/swift-harness:doctor` names it.
  - **Smoke:** a real session blocked once on the project's check, and Claude explained why the references were left as asked.
- New: approval across worktrees ([#107](https://github.com/davidelarocca/swift-harness/issues/107)). With parallel agents in separate worktrees of one repository, the verify command used to need an approval in each. An approval is now also recorded under the repository's git common directory, by a digest of the command and the file contents without the project path. Another worktree whose command and files are identical inherits it.
  - Any difference asks again (the case V-12 of an external review).
  - Another clone, which has its own common directory, never inherits, even with identical files.
  - Revoking in any worktree removes what the worktrees share; each checkout keeps its own local approval.
  - `/swift-harness:approve-verify` and `/swift-harness:doctor` say where the approval comes from.
- New: evidence over time ([#110](https://github.com/davidelarocca/swift-harness/issues/110)). The end-of-turn records are kept as a history, `evidence-history.jsonl` in the project's state folder, one line per record:
  - **Bounds:** at most 2000 lines (`SWIFT_HARNESS_HISTORY_MAX`), and no older than the retention of session folders. A record that only says nothing ran again on the code of the previous one is not repeated.
  - **Concurrency:** trimming takes a lock, so two sessions appending at once lose nothing.
  - **Durations:** each check that ran has its duration in whole seconds.
  - **Catch log:** lines written by the end-of-turn check carry the code identity they are about, and a block carries the check's duration.
  - **Report:** `/swift-harness:report` counts the records of the period by outcome, with the time the checks took.

  Nothing else changes. It is the base for evals over a series of sessions (#8) and for adapters that start in observation (#105).
- New: the adoption audit reads what a project's lint and formatter look at ([#104](https://github.com/davidelarocca/swift-harness/issues/104), [#105](https://github.com/davidelarocca/swift-harness/issues/105)). From `.swiftlint.yml` (`disabled_rules`, `opt_in_rules`, `only_rules`), `.swiftformat` (`--disable`, `--rules`) and `.swift-format` (rules set to false), as text: a lint that passes does not look at the rules it turns off. An experiment planted defects in a copy of two open-source apps and a real app, and ran the projects' own checks on them ([`tests/evals/adapter-sensitivity.md`](tests/evals/adapter-sensitivity.md)). The results:
  - NetNewsWire's strict SwiftLint, clean in CI, caught 1 of 5 lint defect classes; Ice's caught 3 of 5.
  - Every miss came from the config, readable without running anything.
  - So the "sensitive" level is kept for checks without a declarative config, with the user's approval, as information only.
- New: adoption audit, v0 ([#104](https://github.com/davidelarocca/swift-harness/issues/104)). `/swift-harness:setup audit` (`scripts/audit.sh`, `--json`) reports what a project already has, reading its rules, docs, scripts, CI files and manifests as text only. It writes nothing and runs nothing from the project: no project command, script or test, no `swift package dump-package`, not even git, whose repository config can run programs. Files that may hold secrets are listed by path and never opened. For each capability (build, tests, UI tests, docs checks, lint, formatter, security settings, UI test isolation, agent rules, CI, platforms), each source is given a level: *declared* by a document, *configured* by a file, *executed* in the harness's own end-of-turn record, *observed* in the files, or *unknown* with the reason. Records of the past (`docs.history`) are left out, and variants of one command are one row. It ends with a proposed guest setup using the project's own commands, preferring its rules, then its scripts, then its CI, or one inferred from a shared scheme or the test targets and said so. The cost of each command is "not measured", since timing runs them and needs the user's approval. Tests cover zero writes and zero runs (fake tools, sentinel scripts, a git `core.fsmonitor` trap) and the cases V-01, V-07, V-08, V-09, V-15, V-17 and V-18 of an external review. On a fixture, IceCubesApp and a real app with its own tools, the audit gets 21 of 21 adoption decisions right, against 11 for a file-presence checklist ([`tests/evals/adoption-audit.md`](tests/evals/adoption-audit.md)).

- New: Codex runs the same hooks ([#122](https://github.com/davidelarocca/swift-harness/issues/122)). `setup-guest.sh --codex` writes `.codex/hooks.json` and a launcher, `.codex/swift-harness-hook.sh`, which finds the installed plugin and uses Claude Code's plugin data folder, so one approval covers both agents. `scripts/codex-hook.sh` adapts Codex's input:
  - **Edits:** the paths of an `apply_patch` edit, moves included, are read from the patch, and the guard and post-edit checks run once per file.
  - **Questions:** Codex cannot ask the user from a hook, so an edit the guard would ask about is refused, with a reason that tells Codex to stop and ask first.
  - **Records:** the evidence record and the catch log carry the agent (`claude`, `codex`, or the `--agent` name of `check.sh`).

  `--from` copies the Codex files to a new worktree, and `--local` keeps them out of git.

- New: a project check in observation can earn its block ([#105](https://github.com/davidelarocca/swift-harness/issues/105), H2). With `docs.blocking` false, each set of new problems the project's docs check finds is logged once as observed, and as fixed when it goes away. `/swift-harness:report` then proposes, per check:
  - **wait** below 10 observed findings;
  - **block** (set `docs.blocking` to true) when more than 90% were fixed in their session;
  - otherwise, **observe** and look at the findings left first.

## swift-harness 1.7.0 (2026-11-08)

A measured harness. Whether each check catches what it claims, how a project drifts over its history, what every turn actually checked, and what the checks caught, all from facts the hooks hold and kept on your machine. Plus a guest mode for projects with their own rules, a test isolation check, and a branch scope contract. Measuring the checks found real bugs in the plugin itself, fixed here. Checked with 653 hook tests, a check-sensitivity run with real builds in CI, and the full smoke run in real Claude Code sessions (22 scenarios, all invariants pass).

**Upgrading:** nothing to do. Everything new is on by default where it only reports (the evidence summary, the catch log, the scope and isolation checks when configured), or is a command you run. Two things are worth a copy of the new templates: `verify.sh`, so that with Xcode 27 and no xcbeautify the names of failed tests reach Claude; and the test templates (`LayoutContract.swift`, `Snapshot.swift`, `Screenshot.swift` and the others), which now pass the template SwiftLint config in strict mode. A result recorded by 1.6 no longer counts after the update, so the first turn that changes code verifies again.

- New: branch scope contract ([#72](https://github.com/davidelarocca/swift-harness/issues/72)), brought forward from v1.9.0. A long-running branch, such as a port, must change only its own files and take the base branch's work, never push shared files the other way. `scope` in `.claude/swift-harness.json` gives a branch (or a prefix with `*`) its paths and its base (default `main`). A new Stop hook, `scope-watch.sh`, never blocks. At the end of a turn on that branch it tells the user and Claude, once until it changes: the files changed since the branch left the base that are outside the paths, committed or not (shell edits included), and the base's commits not merged into the branch yet. Out-of-scope files go to the catch log.
- New: test isolation and a pitfalls template ([#68](https://github.com/davidelarocca/swift-harness/issues/68)), brought forward from v1.8.0.
  - `uiTests.isolation` lists the launch arguments or environment keys that give the app its own store and defaults in UI tests. `scripts/isolation.sh` (used by `/swift-harness:doctor`) reads the UI test files as text. A file that calls `.launch()` must name one of them, or call a launch helper declared in a file that does: a function with "launch" in its name, not `launch()` itself, or one listed in `uiTests.launchHelpers`. Doctor warns with the file and line; with UI tests and nothing declared, it says that the check could not run.
  - Checked read-only on a real app's 47 UI test files: its 4 files that launch the app all pass, through its argument or its helpers. With the argument removed from one, that file is reported at its line. That run also showed that counting every helper function was too loose: the app declares `launch()`, `close()` and `start()` helpers, which made every file look isolated.
  - Setup offers `.claude/rules/tests.md` (UI tests on their own data, temporary folders for files, a defect found by hand becomes a test and a pitfall) and `docs/PITFALLS.md` (about a dozen traps that cost real time; the checkpoint after a compaction names it). It also fills `uiTests.isolation` from the project's UI tests.
- New: guest mode ([#71](https://github.com/davidelarocca/swift-harness/issues/71)), for a project with its own agent rules, docs and checks that must not change, for example a branch that stays mergeable with one where work continues. `/swift-harness:setup guest` finds the project's own build, test and docs commands, asks the user to confirm them, and runs `scripts/setup-guest.sh`. The script writes two files and nothing else: `.claude/swift-harness.json` (`"guest": true`) and a `verify.sh` whose `fast` and `full` run those commands. No `CLAUDE.md`, rules, docs or templates are written. The formatter and SwiftLint stay off unless the project has their config, so its code is never rewritten in another style. `--no-docs` leaves the docs check to the project's own. The script refuses if either file exists. With a `Scripts/` folder (the same folder as `scripts/` on a default macOS volume) it writes into it under its own name, and the verify command follows. At session start Claude is told that the project's own rules are the source of truth; `/swift-harness:doctor` shows the mode. Tests: on a fixture with its own `CLAUDE.md`, `AGENTS.md` and check script, `git status` shows only the two files, before and after the hooks run, and the end-of-turn check runs and blocks on the project's command.
- New: static HTML report ([#87](https://github.com/davidelarocca/swift-harness/issues/87)), first section. `report.sh --html` (`/swift-harness:report html`) writes `.build/swift-harness/report.html` from the existing outputs only: the last end-of-turn record (each check, its result and detail) and the catch log (per check, the checks not run, the latest entries). It follows the rules of discussion [#50](https://github.com/davidelarocca/swift-harness/discussions/50):
  - read-only, with no script and no network; a Content-Security-Policy forbids both;
  - every section names its source file;
  - only a check that ran and passed on the current code is green, a check not run is grey, and a record about an earlier state of the code says so and shows nothing green;
  - every value from the repository or the log is HTML-escaped. A test feeds a check name `<script>…</script>` and a catch `<img onerror=…>`.

  Light and dark follow the system. The drift curve and the sensitivity matrix come next, in the sections the issue lists.
- New: catch log and `/swift-harness:report` ([#86](https://github.com/davidelarocca/swift-harness/issues/86)). A defect prevented leaves no trace, so the hooks now keep one: every block, report, question and skipped check, and how it ended, is a JSON line in `catches.jsonl` in the project's state folder (time, session, check, kind, what). The log never leaves the machine. Kinds:
  - `blocked`: the end-of-turn check, per failing check, with the attempt; the post-edit lint and contract blocks; docs references broken in the session.
  - `reported`: SwiftLint issues after an edit, with the rules; components the registry does not list; baselines or protected files changed without approval.
  - `asked`: the guard's question before a protected edit.
  - `skipped`: a check that did not run, once per code, with why.
  - `fixed`: a later pass after a block, once per blocked check.
  - `left-failing`: Claude stopped, or the attempts ran out.
  - `approved`: the verify command, snapshots, performance baselines or security settings, approved by the user.

  `/swift-harness:report` (`scripts/report.sh`, `--days N`, `--since DATE`, `--all`, `--json`) summarises it: totals, one line per check with how it ended and the last thing caught, and the checks that did not run. Smoke: in `stop-fails`, the Stops that blocked on the verify command, the log's lines and the report's count are the same number. That run also showed that a missing SwiftLint under `lintBlocking` blocked without being logged as a block; it now is.
- New: evidence summary ([#81](https://github.com/davidelarocca/swift-harness/issues/81)). At every end of a turn, the end-of-turn check writes `evidence.json` (in the session folder, and for the project), from the facts it holds and not from Claude's wording: the code it is about, the outcome (`passed`, `partial`, `failed`, `checked` when only checks other than the verify command ran, `not-verified`, `unchanged` when nothing ran again), and each check with its result and detail. The detail can be the platforms the verify command checked and tested, or why a check did not run: the verify command not approved, `verify.enabled` false, contracts without the approved command, SwiftLint missing, a registry or layout contract in another format. The user hears about it only when something was not checked: the sentence "Not checked this turn: …" is added to the message they already get, or one short line, once per code, says what was checked and what was not. A block tells Claude the same, so it does not report those parts as verified. `/swift-harness:doctor` shows the last turn's checks, and the checkpoint after a compaction lists them. The `ui-change` skill and the `ui-reviewer` agent mark each claim *measured* (a check or test, named), *seen* (a screenshot or the accessibility tree, named) or *inferred* (from the code). Smoke: `verify-unapproved` checks the record, the notice, and that a final message saying the tests pass is backed by a test run in the session.
- New: drift score ([#80](https://github.com/davidelarocca/swift-harness/issues/80)). `/swift-harness:drift` (`scripts/drift.sh`, user only, no hook code) measures the working tree (`score`) or each commit of a git range (`history <range>`, each commit extracted with `git archive`), as a text line or JSON. In the UI code (Swift files outside tests and outside the files the SwiftLint padding rule excludes): padding, stack spacing, corner radius and font size, each use a literal number or a token, as distinct literal values, literal uses and the token share; colors made from components (`Color(red:)`, `Color(hex:)`, `NSColor(red:)`, `#colorLiteral`) as literals. Near-duplicates: a View or ViewModifier the registry does not list whose role, the last word of its name, is a registered component's (`StatusPill` and `Pill`), listed for a person to confirm. And the problems of the registry, layout contract, docs and architecture contract checks. The score adds them up: the things to fix, lower is better. It grows with the code, so each commit also has its UI lines and the literal uses per 1000 of them. `--every N` measures one commit in N for a long history, `--exclude <ERE>` leaves out a design-system package in a project without the SwiftLint config, and colors computed from variables are not literals. A fixture history in `tests/run.sh` (clean, planted drift, clean-up) scores 0, 8, 0. On four years of an open-source SwiftUI app ([`tests/evals/drift.md`](tests/evals/drift.md)): the token share falls from 59% to 46% and the distinct literal values grow from 11 to 40; a jump in the curve is one commit that adds the same hardcoded radius twelve times.
- New: check sensitivity, part 1 ([#79](https://github.com/davidelarocca/swift-harness/issues/79)). A check can pass for the wrong reason: the layout check of 1.4.0 accepted content 2000 pt wide on a real app while every test was green. `/swift-harness:check-sensitivity` (`scripts/mutate.sh`, user only) copies the project into a temporary folder (without `.git`, `.build` and DerivedData, with a fresh git repository), runs the registry, layout contract, docs, security and architecture contract checks once without mutations, then plants one defect at a time and runs them again: a Components entry renamed (registry), a Screens view renamed (layout), a local link or a path in backticks moved to a file that does not exist (docs), an entitlement relaxed (security), a target given a dependency on a sibling its contract does not allow (contracts). Each operator changes one site, chosen the same way every run, and the file is restored before the next one. A mutation is killed when a check fails with a problem it did not report before (line numbers ignored), so a check that already fails still counts. The report is a table: the site as `file:line`, the check it targets, killed or SURVIVED, and every check that noticed it. A survived mutation is a finding, not a failed run (exit 0). A new fixture, `tests/fixtures/mutate/`, is killed by every operator in `tests/run.sh`; a check turned off (`security.enabled` false, approved) is shown to let its mutation survive. Next: results on a real app in `tests/evals/`.
- New: check sensitivity, part 2 ([#79](https://github.com/davidelarocca/swift-harness/issues/79)). `mutate.sh --verify` also runs `scripts/verify.sh full` on the copy, once without mutations and once per operator, for the checks inside the project's tests and SwiftLint: a padding token replaced by a number (lint), a `.keyboardShortcut` removed from a view a `KeyboardCheck` test hosts (keyboard), the first Screens view made 200 pt wider than its Min, on the same line (layout sizes), an `.accessibilityLabel` removed (accessibility), a padding made 3 pt larger in a view a snapshot test renders (snapshots). Verify prints one block, so a new failure is credited to a check by what it names: a SwiftLint rule on the mutated file, or a test file (or a type declared in it) that calls the check's API; numbers are ignored when comparing with the run without mutations. A failure credited to no check is shown as `verify`, often a mutation that did not build. The copy now lives in the project's `.build/swift-harness/`, removed at the end: in the system temporary folder the path goes through a symbolic link and SwiftLint baselines match nothing (SwiftLint 0.65). A new script, `tests/mutate-fixture.sh`, runs it with real builds on a package with the setup templates (its snapshot approved on the machine first) and on the accessibility app: every operator is killed by the check it targets; it runs in CI as a job of its own. `tests/run.sh` covers the rest with a fake verify (crediting, a verify that already fails, a mutation that does not build).
- New: check sensitivity, part 3 ([#79](https://github.com/davidelarocca/swift-harness/issues/79)). Method and results in [`tests/evals/check-sensitivity.md`](tests/evals/check-sensitivity.md): every operator is killed by its target on the fixtures. On a copy of a real ~97k-line app that does not use swift-harness, the docs and security operators are killed, five operators find no registry, layout or architecture contract, four find no check in use, and the accessibility label removal survives: it is on a screen the one audited UI test never opens (coverage, not a bug in the check). From that run: an audit called through a helper function of the project (`app.assertAccessibility(...)`) is now credited (tests that call a helper declared in a test file that calls the API), test file names with regex characters (`XCUIApplication+Layout.swift`) no longer break the crediting, and a verify operator whose check the project does not use (no test calls its API, or no SwiftLint padding rule) is reported as `no check` without a verify run, instead of costing a build and showing as a survivor.
- Fix, found by the run above: the setup test templates (`LayoutContract`, `Snapshot`, `Screenshot`, `LayoutAudit`, `FocusOrder`, `PerformanceBudget`, `KeyboardCheck`) broke the template `.swiftlint.yml` in 59 places (line length, identifier names and others). `scripts/verify.sh full` lints in strict mode, so a project that copied them failed verification on code it did not write. Each template now turns off only the rules it breaks, and turns them back on at its end.
- Fix, found by the run above: with Xcode 27, `xcodebuild -quiet` names failed tests only in a "Failing tests:" list, one per indented line, and `scripts/verify.sh` without xcbeautify kept only `** TEST FAILED **`: Claude was told tests failed, not which. The list is now kept. **Upgrading:** copy the new `verify.sh` template, or add `|^Failing tests:|^[[:space:]]+[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z_][A-Za-z0-9_]*)+\(\)$` to the `grep -E` of its xcodebuild step.

## swift-harness 1.6.1 (2026-11-07)

A partial verification is no longer recorded as a pass. Found by an external review of 1.6.0 and confirmed in the code.

- Fix: a `PARTIAL` result of the generated `scripts/verify.sh` (a platform listed in `PLATFORMS` that no build or test reached, such as iOS in a packages-only project) exits 0 by design, and the end-of-turn check recorded it as a plain pass: `/swift-harness:doctor` and the checkpoint after a compaction said "passed on the current code", and Claude was never told. Now the script ends with a versioned line for the hooks, `swift-harness-result/1: <passed|partial|failed>; checked: <platforms>; tested: <platforms>; not checked: <platforms>` (in `fast` mode a scheme is built, not tested, and `tested` says so). The end-of-turn check reads the last such line, and the `PARTIAL` line of scripts generated before 1.6.1. It keeps the outcome and the platforms in the state folder. A partial pass does not block; the user (`systemMessage`) and Claude (`additionalContext`, which does not block) are told once for that code what was not checked. `doctor` and the checkpoint say `PARTIAL` with the platforms, and a full pass names the platforms built and tested. The line can only lower the outcome: an exit other than 0 is a failure whatever it says, and `failed` with exit 0 is a failure. A custom verify command without the line passes on exit 0 as before, with its platforms reported as unknown.
- CI: the hook tests job installs SwiftLint, so the template rules' tests (concurrency, Reduce Motion) run there too instead of being skipped. `tests/run.sh` now counts 542 checks on a Mac and 537 in CI, where the performance budget comparisons are replaced by one not-compared check (CI virtual machines count no instructions). The 1.6.0 notes said 528 for both; CI ran 511.
- Roadmap: test isolation from real user data ([#68](https://github.com/davidelarocca/swift-harness/issues/68)) moves to the start of v1.8.0, before the navigation crawler and the injected faults, which run on real apps.

**Upgrading:** nothing to do. A `scripts/verify.sh` generated before 1.6.1 is read through its `PARTIAL` line; copy the new template to get the full line (platforms built and tested).

## swift-harness 1.6.0 (2026-11-07)

Reliable sessions and checks on what the app does, not only how the code looks: per-session state for parallel sessions, keyboard and focus checks, a layout audit from the accessibility tree on macOS and iOS, a docs reference check, and performance budgets that only you approve. Each check was measured before it was built: spikes on GitHub runners and a real Mac, published in the issues. Checked with 528 hook tests, UI test fixtures on macOS and an iPhone simulator in CI, smoke scenarios in real Claude Code sessions, and the docs of a real ~97k-line app.

**Upgrading:** one thing applies to existing projects without any setup: the docs reference check is on by default (`docs.enabled`). The first session after the update takes the docs problems already there as its start: they do not block, and `/swift-harness:doctor` lists them. From then on, a link, path or section broken during a session blocks the end of that turn once. Per-session state needs nothing from you. Everything else is opt-in through the setup templates: `KeyboardCheck.swift`, `FocusOrder.swift`, `LayoutAudit.swift`, `PerformanceBudget.swift`, and the `ds_motion_without_reduce` SwiftLint rule.

- New: performance budgets with approved baselines ([#33](https://github.com/davidelarocca/swift-harness/issues/33)). A spike measured what is stable enough to budget. On a Mac, instructions retired by the test process (`proc_pid_rusage`) vary by about 0.25% between runs of the same code, and decoding the same data twice raised them by 64%. On GitHub's macOS runners (virtual machines) there is no instruction counter, and time varies by ±20% between runs, enough to hide that 64%. Tests running in parallel in the same process inflate the count (361 M to 765-850 M) and spread the iterations (0.01% to 7-18%). So: the setup template `tests/PerformanceBudget.swift` measures an operation (3 warm-ups, 15 iterations, the median) and compares it with a baseline in `performance/` (`performance.path`), pinned to the architecture, the macOS version and the build configuration. More than 5% over fails with the numbers. More than 5% under passes and leaves the numbers to approve. Iterations spread by more than 2% fail as unstable. Without a counter, or on another machine, the result is not compared, with the numbers printed. Baselines are written only by the new `/swift-harness:approve-performance` (`scripts/performance.sh`, user only): the guard asks before an edit of the folder, the end-of-turn notice (`snapshot-watch.sh`, now for both kinds of baselines) reports changes made without approval, and the folder is part of the verify fingerprint. `setup` offers it for two or three key operations, in an XCTest class in a package test target, so `fast` runs it. `doctor` lists the baselines and what waits for approval. Not measured: time spent waiting (I/O, locks, the main thread), hangs and memory growth. CI runs the fixture's not-compared path; the comparisons run in `tests/run.sh` on a Mac. Fix: `doctor` now knows the `docs` keys of #70 and checks their types, so they are no longer reported as unknown. **Upgrading:** nothing changes until you copy the new template.
- New: docs reference check ([#70](https://github.com/davidelarocca/swift-harness/issues/70)). `scripts/docs.sh` reads the project docs (`docs.paths`: `CLAUDE.md`, `AGENTS.md`, `docs/`) as text and reports, as `file:line`: a Markdown link to a file or heading that does not exist; a path in backticks that does not exist (two or more parts, ending with an extension or a slash, whose first folder is in the project; not in records of the past, `docs.history`, nor in ignored files or folders the harness creates later, `docs.ignore`); a section named in quotes beside a doc (`"Presented UI" in docs/LAYOUT_CONTRACT.md`) that the doc does not have as a heading, the lead of one, a bold label or a table row; an `@` import of a missing file; and the files read into every session (`CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md` and their imports) over `docs.budget` bytes (20000, about 5000 tokens). Code blocks, HTML comments and `{{placeholders}}` are skipped. A new Stop hook, `docs-watch.sh`, blocks the end of a turn once for problems new in the session (those already there at session start do not block, and a problem that only moved lines is not new); if Claude stops again without fixing them, the user is told. Docs stay out of the verify fingerprint, so a docs edit never re-runs the build. `/swift-harness:doctor` shows the result and the session size. Checked on a ~97k-line app's 55 docs and 1161 references: the first version reported 203 problems, almost all false (sections named after table rows and bold labels, paths inside a module or on disk, old notes kept in an archive); with the rules above it reports one, a real one (a file moved into a folder). - New: layout audit from the accessibility tree in UI tests, on macOS and iOS ([#69](https://github.com/davidelarocca/swift-harness/issues/69)). At the end of each turn that changes code or the registry, `scripts/registry.sh` reads `docs/COMPONENT_REGISTRY.md` and fails the turn when a File does not exist or does not declare the component's Name, when an ID or name is listed twice, or when a Retired ID is still listed, naming the registry line. It reads Markdown only, so it runs without the verify approval. After an edit in `registry.sources`, Claude is told which views, modifiers and styles in that file the registry does not list, and which entries point to it. `/swift-harness:doctor` shows the result and the components not listed. New config keys `registry.enabled`, `registry.path`, `registry.sources`; the registry template gets an Internal section. **Existing projects:** a registry with a stale entry now blocks the end of a turn until it is fixed (`/swift-harness:doctor` shows it first, `registry.enabled: false` turns the check off); add `registry.sources` to find unlisted components.
- New `/swift-harness:product-map` ([#30](https://github.com/davidelarocca/swift-harness/issues/30)): a read-only map of the product from its code: entities, their pages, every place each one appears, relations, collections the user creates or organizes, and action sets. It lists the gaps with `file:line` evidence and a priority: items you cannot open from where they are shown, related items shown as plain text (or styled as links that do nothing), collections without rename, reorder, delete or undo, actions offered in some places and not others. It writes `docs/PRODUCT_MAP.md` after you approve. On a real ~97k-line app it found the missing cross-links that a generic UX review of the same code did not.
- The product map guides daily work: `setup` adds an empty `docs/PRODUCT_MAP.md` and links it from `CLAUDE.md` and the architecture hub; the UI rule, `feature` and `ui-change` read it before showing an entity in a new place (open it, reach the related entities shown with it, offer its usual actions) and update it in the same change; `ui-reviewer` checks product coherence. Existing projects: run `/swift-harness:product-map`, then add the line to `CLAUDE.md` it suggests.
- `/swift-harness:setup` finds the app's security settings (`*.entitlements`, app `Info.plist`, `PrivacyInfo.xcprivacy`) and proposes them as protected paths, file by file, so Claude asks before relaxing an entitlement to make something work. Existing projects: add those paths to `protectedPaths` in `.claude/swift-harness.json`.
- Smoke suite: a `product` group of 3 scenarios (`tests/smoke/run.sh product`, not in the default run). Showing tasks due today on Home: with the plugin, every row opened the task, the project name opened the project and the shared task menu was used; without it, the project name was plain text. One run each, recorded in `tests/smoke/RESULTS.md`.
- Tests: every skill is named like its folder, every `${CLAUDE_PLUGIN_ROOT}` path a skill cites exists, every docs and rules template is in the setup table, and every doc linked from the templates has one.

## swift-harness 1.2.0 (2026-11-06)

Trust and onboarding. **Upgrading:** the end-of-turn check runs nothing from the repository until you type `/swift-harness:approve-verify` once in each project (and each worktree). Claude is told at session start, and `/swift-harness:doctor` shows it.

- **Breaking for existing projects:** the end-of-turn check runs the repository's `verify.command` only after you approve it ([#6](https://github.com/davidelarocca/swift-harness/issues/6)). Type `/swift-harness:approve-verify` once per project (and per worktree) after updating. Until then nothing from the repository runs, Claude is told at session start, and you get one warning per code state. The approval is stored in the plugin data folder, outside the repository, and covers the project path, the command and the content of each file it names: change any of them and the check asks again. `/swift-harness:approve-verify revoke` removes it. `lintBlocking` keeps working without the approval, but a clean lint alone is not recorded as a passed verification.
- `/swift-harness:setup` ends by asking you to approve the generated verify command.
- New `/swift-harness:doctor` ([#12](https://github.com/davidelarocca/swift-harness/issues/12)): a read-only diagnosis of the project's setup, one PASS / WARN / FAIL / INFO row per check with the fix. It checks jq, Xcode, the formatter and SwiftLint, unknown or invalid config keys, `{{...}}` placeholders left in generated files, protected paths that do not exist, the verify script (present, executable, scheme or packages set, packages that exist) and its approval, `.swift-format` with swift-format, the SwiftPM layout (for the planned architecture contracts) and the last verification of the current code. It changes no file and creates no state folder.
- A verification result now belongs to the code and to the plugin version ([#18](https://github.com/davidelarocca/swift-harness/issues/18)). Before, a pass recorded by an older version still counted after an update that made the checks stricter. Now unchanged code is verified again once after an update. The project's policy (`lintBlocking`, `verify.command`) was already part of the code state.
- More build inputs count as changes: workspaces (`contents.xcworkspacedata`), and every file under a SwiftPM `Sources/` or `Tests/` folder, so resources outside `Resources/` and test fixtures trigger the check. Xcode per-user state (`xcuserdata`) and `.DS_Store` are ignored.
- SECURITY.md describes what the approval covers and what it does not: files the command reads without naming them, the build itself (Run Script phases, SwiftPM manifests and plugins), and Claude Code's own project hooks. The "never does" guarantee now covers only the plugin's own scripts: an approved verify command runs with your permissions, and even the generated `verify.sh` downloads dependencies and writes SwiftPM and Xcode caches outside the project.
- Smoke suite: 11 scenarios. New: `verify-unapproved`, `approve-verify` and `doctor`.
