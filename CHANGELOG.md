# Changelog

## Unreleased

- New: layout audit from the accessibility tree in UI tests, on macOS and iOS ([#69](https://github.com/davidelarocca/swift-harness/issues/69)). A spike on a GitHub runner (macOS 26, iPhone simulator) and on macOS 27 measured what the tree shows: frames are not clipped, so content past an edge keeps its whole frame; content of a scroll view or list reports frames outside it; a truncated text gives only its visible part; a text with opacity 0 is absent on macOS and present on iOS. So: the setup template `tests/LayoutAudit.swift` reads the tree of the launched app once and fails for every element cut by the edge of its window, sheet or popover outside a scroll view, and every text over another text (texts in a scroll view are compared only with each other), with frames and the edge; exceptions name the element and need a reason, and one that matches nothing fails. `LayoutAudit.shrinkWindow(app)` drags a macOS window to its minimum size with a click-drag (a press-drag does not reach the window on macOS 27; setting the size through the accessibility API is refused to the test runner) grows it once when it does not move (macOS restores the last frame, which can already be the minimum), and fails if the window cannot be resized. On iOS, `LayoutAudit.largestText` launches at the largest Dynamic Type size; an app without a launch screen runs at the legacy 320x480 size, which the header and setup point out. `setup` offers it next to the accessibility audit. CI runs a fixture app on macOS and on an iPhone simulator: two fixed-width buttons cut at the smallest window and on an iPhone, and two overlapping labels, are found; the scrolling track list and the footer under it are not; the fixed screen passes; in a wide window the buttons fit; an exception covers only its own element. Not measured, and listed in the header: text cut by its own frame, elements hidden from VoiceOver, content under the iOS status bar or home indicator, empty space. **Upgrading:** nothing changes until you copy the new template.
- New: keyboard, focus order and Reduce Motion checks for shared components ([#52](https://github.com/davidelarocca/swift-harness/issues/52)). A spike measured on macOS 27 what a test can see; CI confirms it on macOS 26. In a test process, keys sent to a view in an offscreen window reach `.keyboardShortcut` (default and cancel actions, Command shortcuts), `onKeyPress` and `onExitCommand`; Tab does not move focus, and Reduce Motion cannot be set (`accessibilityReduceMotion` is read-only). In a UI test, Tab moves focus through buttons and toggles only with Keyboard navigation on in System Settings (a launch argument does not do it), and focus is readable only through an undocumented attribute. So: the setup template `tests/KeyboardCheck.swift` presses keys on a component in a unit test and the test asserts what happened (runs in `fast` in a package); `tests/FocusOrder.swift` checks in a UI test that Tab visits the controls in the given order, wraps, and that Shift-Tab goes back, and is skipped, not passed, when Keyboard navigation is off; the design system reference gets `@ReduceMotion` (the system setting, overridable by tests and previews with `.environment(\.reduceMotionOverride, true)`) and `Motion.moving(_:reduced:)` (no moving animation, a fade for a moving transition), used by the pill presenter; a new SwiftLint rule, `ds_motion_without_reduce`, reports a moving transition that skips it. Setup, the UI rule, `ui-change`, `design-system` and `ui-reviewer` say what is measured and what stays a review (click-only actions, focus rings, menu shortcuts, `withAnimation`). CI runs a keyboard fixture (a pointer-only card is the negative control), the Reduce Motion override on a fixture component, and the focus order on the accessibility fixture with Keyboard navigation on: a wrong order and a control left out of the Tab loop fail. In a test process, shortcuts that differ only by Shift are not told apart reliably, so they stay with UI tests. **Upgrading:** nothing changes until you copy the new templates; the new SwiftLint rule is in the template only.
- Fixed: two sessions on one folder shared their starting lists ([#61](https://github.com/davidelarocca/swift-harness/issues/61), found in an adversarial review of #11 and #32). The hooks kept what a session compares with at the end of each turn in one folder per project path, so a second Claude Code session started in the same folder replaced the first session's lists, and a change the first session made through the shell before that moment was no longer reported to it. What a session started with (the code baseline, protected files, snapshot baselines, the architecture contract, the approved security settings, the session's head and changed files for the checkpoint) and the notices it already showed now live in a folder per `session_id`. Approvals, the security baseline, the last verification result and the files pending under `lintBlocking` stay per project, shared on purpose. An edit you were asked about and an approved snapshot count for every session open on the project. Session folders untouched for 14 days are removed at session start. Separate git worktrees were never affected. **Upgrading:** nothing to do; the first session after the update moves to the new layout.

## swift-harness 1.5.0 (2026-11-07)

iOS-aware checks, a read-only porting audit for macOS apps, and new guardrails: security settings that only you approve, concurrency escape hatches that need a reason, shell changes to protected files reported, a checkpoint after compaction, and an accessibility audit for UI tests. Checked with 469 hook tests, a CI job on an iPhone simulator, real UI tests on macOS 26 and 27, 21 smoke scenarios in real Claude Code sessions, an adversarial review, and a porting run on a real ~97k-line app.

**Upgrading:** two things apply to existing projects without any setup. (1) The first session after the update records the app's security settings (entitlements, App Transport Security, signing build settings) as a baseline, shown as not reviewed in `/swift-harness:doctor`; from then on, a change to them fails the end-of-turn check until you approve it with `/swift-harness:approve-security`. Review the baseline once with that command. Set `security.enabled` to `false` to opt out (itself a change to approve once a baseline exists). (2) Files under `protectedPaths` changed through the shell are reported at the end of the turn. A `scripts/verify.sh` generated before 1.5.0 keeps building for macOS (no `PLATFORMS` line); add `PLATFORMS` and `IOS_SIMULATOR` from the template to check iOS. The new SwiftLint rules and the accessibility helper are opt-in through the templates. The README still says macOS: iOS support is checked on a real app before that changes (#40).

- New: accessibility audit in UI tests ([#36](https://github.com/davidelarocca/swift-harness/issues/36)). The setup template `tests/AccessibilityAudit.swift` runs Apple's `performAccessibilityAudit()` on a screen of the launched app (missing descriptions, contrast, hit areas, clipped text, traits) and fails for every issue, except exceptions listed in the test with the element, the issue type and a reason; an exception without a reason fails. `setup` offers it for apps with a UI test target, one test per main screen, in `scripts/verify.sh full`. Measured on macOS 26 (GitHub runner) and 27: the audit also reports parts of the window and screen the system draws, which no app can fix (the root group of a SwiftUI window, without a description; the window buttons at the left of the title bar; the window title, whose contrast fails when the window is not key; the system menu bar above the windows); the helper skips exactly these by default, keeps auditing the app's own menus and toolbar items, prints each one it skips, and `skipWindowChrome: false` shows them. CI runs a fixture app with real UI tests: the audit finds its button without a description, the fixed screen passes the full audit, an exception silences only its own issue, and with the chrome not skipped the other issue still fails.
- New: a checkpoint after compaction ([#10](https://github.com/davidelarocca/swift-harness/issues/10)). When Claude Code compacts the context, the session-start hook (now also on `compact`) gives Claude a few lines of facts the hooks recorded, which a summary can lose or get wrong: the branch, commits and files changed since the session started, the verification result on the current code (passed, FAILED, not verified, or only lint and contracts checked), what waits (lint errors under `lintBlocking`, an unapproved verify command, unapproved security changes, protected files changed outside Edit and Write), and the project docs to reread. The session baseline is kept: a compaction never makes changed code look verified.
- New: protected files changed through the shell are reported ([#11](https://github.com/davidelarocca/swift-harness/issues/11)). The guard asks before Claude edits a protected path with Edit or Write, but a shell command (`sed`, `cp`, `mv`, `rm`, a script) was not seen. Session start now records the files under `protectedPaths`; a new Stop hook, `protected-watch.sh`, tells you which ones changed, appeared or were deleted outside those tools, once per change, and never blocks. An edit you were asked about is not reported, including the formatter's rewrite after it. Detection, not prevention: permission rules remain the way to block writes.
- New: a ratchet on concurrency escape hatches ([#37](https://github.com/davidelarocca/swift-harness/issues/37)). The SwiftLint template has four rules, as errors: `@unchecked Sendable`, `nonisolated(unsafe)`, `@preconcurrency` (imports and conformances) and `.assumeIsolated`. A use with its reason on the same line (`// concurrency: <why it is safe>`) passes; comments and strings are ignored; the SwiftLint baseline keeps the ones already in the project. The architecture rule template says what to try first (actor, `@MainActor`, `Mutex`, Sendable values, `await`) and when an escape hatch is acceptable. Tested with the real SwiftLint and the template.
- New: security settings contract ([#32](https://github.com/davidelarocca/swift-harness/issues/32)). `scripts/security.sh` reads the app's security settings without running project code: every key of each `*.entitlements` file, the `NSAppTransportSecurity` dictionary of `Info.plist` files, and the signing and capability build settings in `project.pbxproj` and `.xcconfig` files (hardened runtime and its exceptions, App Sandbox and its access settings, entitlements file, extra signing flags), with how many configurations set each value. The first session records them as a baseline in the plugin data folder, outside the repository. From then on, any change (a new hardened runtime exception, the sandbox removed, hardened runtime off in one configuration, an ATS exception, a new entitlements file) fails the end-of-turn check with the lines that changed, and Claude is told to revert it or stop and ask; it needs no verify approval, since nothing runs. New `/swift-harness:approve-security`, run only by the user: it explains each change, flags the ones that weaken protection, and records the new state when the digest shown is still current. `/swift-harness:doctor` reports the baseline, unapproved changes and the new config key `security.enabled`. Protected paths still ask before Claude edits these files; this also catches changes made through the shell or Xcode. The first baseline is recorded, not approved: `/swift-harness:doctor` shows it as not reviewed (with the settings in it that already weaken protection) until you approve it, since a new clone, Mac or worktree starts from what is on its branch. Turning `security.enabled` off is itself a change to approve, code signing identity and `CODE_SIGNING_ALLOWED` are covered, and every approval made during a session is shown to you at the end of the turn, whoever ran the script.
- New: `/swift-harness:port-to-ios`, a read-only porting audit ([#47](https://github.com/davidelarocca/swift-harness/issues/47)), run only by the user. `scripts/porting.sh` scans the Swift files as text: macOS-only API compiled for iOS (`import AppKit`, AppKit types, `MenuBarExtra`, `Settings`, `Window` scenes, split views, window modifiers, security-scoped bookmark options) blocks a module, with `file:line`; code inside `#if os(macOS)` or the iOS-excluded branch of an `#if` is guarded; hover, keyboard shortcuts, tooltips, menu commands, context menus, drag and drop, popovers and file pickers are UI adaptations. Comments and strings are ignored. The summary adds the declared platforms (shared with doctor) and the platforms of pinned dependencies with a local checkout. The skill classes each module and feature (share as is, with adapter, UI adaptation, redesign, unavailable, not assessed), compares target structures and recommends one, offers an iOS Simulator build of the packages only after the user says yes, and writes `docs/PORTING_PLAN.md`, checking with `git status` that nothing else changed. The status per platform never says ready. Checked in a real Claude Code session on a copy of a ~97k-line macOS app ($1.52): the only file that changed was `docs/PORTING_PLAN.md`; 15 claims spot-checked against the code, all true (including negatives such as no `AVAudioSession` in the sources); iOS stayed "not built" without the user's yes; the plan followed the product direction recorded in the project's own decision log instead of inventing one, compared two target structures and left the choice to the user. The session also found what the scan missed, now covered: C and Objective-C files (a module including IOKit headers), and `iTunesLibrary`, `DiscRecording`, FSEvents and the Core Audio HAL.
- CI: an iOS fixture ([#40](https://github.com/davidelarocca/swift-harness/issues/40), third part). `tests/ios-fixture.sh` generates `scripts/verify.sh` for a package that declares macOS and iOS and runs it with real Xcode: `fast` builds both, an error only in the iOS build fails with `failed on: iOS`, packages only is `PARTIAL`, doctor finds both platforms and the simulator. With `--full` (the new CI job, on a GitHub macOS runner) the tests run on macOS and on an iPhone simulator, and a negative control that fails on iOS only proves the iOS tests really run.
- New: UI guidance per platform ([#40](https://github.com/davidelarocca/swift-harness/issues/40), second part). `ui-change`, `ui-reviewer`, the `design-system` skill and the UI rule template follow each platform the view runs on: on iOS, Dynamic Type (text styles, layouts that reflow at accessibility sizes), the safe area, touch targets of at least 44 pt, size classes including iPad Split View and Slide Over, no hover-only actions; on macOS, hover, focus, keyboard, menus and windows. The design system skill has an iOS and multiplatform section (differences inside components, `#if os(...)` only where behavior differs). The layout, screenshot and snapshot helpers are stated as macOS only: for a view that builds only for iOS, Claude and the reviewer say that nothing measured it. The component registry also detects `UIViewRepresentable` and `UIViewControllerRepresentable`.
- New: platforms in the verify script ([#40](https://github.com/davidelarocca/swift-harness/issues/40), first part). The generated `scripts/verify.sh` has `PLATFORMS` (`"macOS"`, `"iOS"` or both) and `IOS_SIMULATOR`. `fast` builds the scheme for each platform, iOS for any simulator without booting one; `full` runs the tests on each, iOS on the named simulator. The result names the platforms checked and, on a failure, the ones that failed. A listed platform that got no build or test (packages only, since `swift test` runs on this Mac) gives `PARTIAL`, never `PASS`, with exit 0. An unknown platform, a scheme with no platform, or iOS tests without a simulator are `NOT CONFIGURED`. `/swift-harness:doctor` reads the platforms from `project.pbxproj` (`SUPPORTED_PLATFORMS`, `SDKROOT`) and `Package.swift` (`platforms:`) and warns when one is not built by the verify script, or is one it cannot build yet (visionOS, tvOS, watchOS, Mac Catalyst); it fails when `IOS_SIMULATOR` is empty or not an available simulator. `setup` detects the platforms and fills both settings. **Existing projects:** a verify script generated before this release has no `PLATFORMS` and keeps building for macOS; doctor reads it as macOS. The README still says macOS: iOS support is checked on a real app before that changes.

## swift-harness 1.4.1 (2026-11-06)

A fix from the real-app check of the layout contract.

- Fixed: the layout contract passed screens it could not measure ([#34](https://github.com/davidelarocca/swift-harness/issues/34), found on a real app). `NavigationSplitView`, `HSplitView`, `List`, `Table` and `.frame(minWidth: 0, maxWidth: .infinity)` take any width they are offered, so `sizeThatFits` never sees what they clip: an element 2000 pt wide in a split view's detail column measured 900 pt in a 900 pt window. On a copy of a ~97k-line app, both main screens (a split view and an equalizer panel) passed this way. `LayoutContract.check` now tells three cases apart. Content that takes any width and asks for none (split views, lists, tables) fails with "its width cannot be measured" and what to do: one row per page of the detail column and for the sidebar, at the width their column gets, and the window type as View for the split view's row; its height is still measured. Content that takes any width but has one of its own (text that wraps, or a stretched frame, which cannot be told apart) passes with a note on the test output. On that app the split view now fails with the fix and the panel gets the note. The window checks were right on that app and are unchanged. `setup`, the contract template and the README explain it. **Existing projects:** a row whose View is a split view or a `List` now fails with that message; follow it, or name the window type as View.

## swift-harness 1.4.0 (2026-11-06)

Visual coherence: screens that hold up at every window size, reviewed as they look, and shared components compared with images you approved. **Upgrading:** nothing needs a change; the layout contract, screenshots and snapshot tests are opt-in through `/swift-harness:setup`. Two things apply to every project: a folder named `snapshots/` at the repo root (or `snapshots.path`) is now guarded (edits ask first, changes without approval are reported at the end of the turn) and counts as a build input. If your project uses that name for something else, set `snapshots.path` to another folder.

- New: a layout contract for window sizes ([#34](https://github.com/davidelarocca/swift-harness/issues/34)). `docs/LAYOUT_CONTRACT.md` gives each main screen its Min, Default and Max size, a width below which it switches to a compact layout, and the popovers and windows it opens. The setup template `tests/LayoutContract.swift` measures each screen in the project's own tests with `NSHostingController.sizeThatFits(in:)`: it fails when the content needs more room than a size gives ("at 560x400 it needs 857 pt of width"), when a window declares a smaller minimum than Min (it can shrink to nothing) or a larger one, and when it grows past Max. At the end of each turn `scripts/layout.sh` checks the contract is true: views and windows exist, every one is measured by a test, sizes are sizes. It reads text only, so it runs without the verify approval. Claude gets the sizes after editing a screen's file; `setup`, `ui-change`, the UI rule and `ui-reviewer` use the contract. New config keys `layout.enabled` and `layout.path`. Truncation, overlaps and where popovers open are not measured: they stay in review.
- Fixed: a component registry without an ID column (documented as optional) failed the end-of-turn check with "the File cell is empty". Empty cells were merged when the rows were read; they are now kept.
- Smoke suite: a `layout` group of 6 scenarios (`tests/smoke/run.sh layout`, not in the default run), each arm measured the same way after the session. One run each: on a small app the baselines also built adaptive layouts; asked for chips on one line that cannot fit, Claude left the contract and the window minimum alone and asked, once after the layout test it ran reported the width needed. Recorded in `tests/smoke/RESULTS.md`.
- CI runs the Swift fixture `tests/fixtures/layout` with the template helper itself: screens that break at their minimum fail, screens that hold pass.
- New: design review on screenshots ([#35](https://github.com/davidelarocca/swift-harness/issues/35)). The setup template `tests/Screenshot.swift` renders a screen in an offscreen window at the Min and Default sizes of its layout contract row (or given sizes), in light and dark, and saves PNG images with metadata (screen, state, platform, size, scale, OS, source file) to `.build/swift-harness/screenshots/`. `ui-reviewer` has a new check, Rendered UI: it opens the images and reports alignment, spacing between screens, hierarchy, truncation and contrast, tied to the image and the `file:line`, as review notes. New config key `screenshots.path`, known to `/swift-harness:doctor`. `ImageRenderer` and `cacheDisplay` were tried and rejected: they draw placeholders for `List` or drop SwiftUI text. ScreenCaptureKit fails inside a test process, so the helper uses the window server capture, looked up at run time to avoid a deprecation warning.
- Smoke suite: a `visual` group (`tests/smoke/run.sh visual`), `ui-reviewer` with and without screenshots, 3 runs each. Planted defects were found by both arms; with images the reviewer gave measured positions, made no wrong claim about the layout (code only: 1 of 3) and found an unplanted rendering defect 3 of 3 times (code only: 0). Recorded in `tests/smoke/RESULTS.md`.
- CI runs the Swift fixture `tests/fixtures/visual` with the capture helper, and uploads the images as an artifact.
- New: visual regression with approved baselines ([#9](https://github.com/davidelarocca/swift-harness/issues/9)). The setup template `tests/Snapshot.swift` renders a component or screen with the screenshot helper, in light and dark, and compares each image with an approved baseline in `snapshots/` (new config key `snapshots.path`). A test never writes a baseline: a missing or different image fails, naming the region that changed in points ("85 of 151200 pixels differ, within x 96-110, y 118-126 pt"), and leaves the new image and a diff with the changed pixels in red under `.build/swift-harness/snapshots/`. `locale:` sets the language and text direction, so a gallery covers long languages and right to left. Baselines are pinned to the macOS version and display scale they were made on: elsewhere (GitHub's runners) an image is reported as not compared, never as a match. Measured on macOS 27: `dynamicTypeSize` does not change how SwiftUI text is drawn on macOS, so accessibility text sizes are not a variant. Focus, keyboard and Reduce Motion checks moved to [#52](https://github.com/davidelarocca/swift-harness/issues/52).
- New `/swift-harness:approve-snapshots`, run only by the user: it lists the new images with their diffs and the macOS they were made on, and copies the approved ones into the baselines folder. The approval is refused when a test ran again since the list was shown. The guard asks before Claude edits the baselines folder, and at the end of a turn you are told about baselines changed without approval, also through shell commands (`cp`, `mv`, `rm`). Baselines are part of the checked code state. `/swift-harness:doctor` shows how many baselines there are, the macOS they were made on, whether this Mac compares them, and images waiting.
- `setup` offers a snapshot gallery for the registry's components; `ui-change`, the design system rule and the `CLAUDE.md` template say a failing snapshot is a defect to fix or a change to show the user, never a baseline to replace. The `design-system` reference snapshot test uses the template helper instead of swift-snapshot-testing, which writes missing references itself and draws through `cacheDisplay` (it drops SwiftUI text, #35). `Screenshot.capture` takes `locale:` too.
- CI runs the snapshot tests of the visual fixture: baselines made in the test are compared, and the committed gallery baselines (made on macOS 27) are reported as not compared on the runner.

## swift-harness 1.3.1 (2026-11-06)

Fixes from an external audit of 1.3.0 (SH130-01 to SH130-08), each reproduced on 1.3.0 and covered by a test that failed before the fix.

- **No pass without the verify command** (SH130-01): with `verify.enabled: false`, or the command not approved, a turn where only the component registry or SwiftLint ran was recorded as passed, and `/swift-harness:doctor` showed "Last verification: passed on the current code" although no build or test had run. Now such a result is recorded apart, with the checks that ran: doctor shows it as a warning ("only component registry passed; build and tests were not run"), it is not re-run on unchanged code, and approving the command later runs it on that code.
- **Inputs outside the project are refused** (SH130-03): 1.2.1 said a `verify.inputs` path outside the project is refused, but `/swift-harness:approve-verify` only showed it as "not covered" and approved anyway. The approval is now refused until the entry is removed.
- **Links in a `verify.inputs` folder are covered** (SH130-04): a link inside a watched folder did not count, so changing the file it points to, or pointing it elsewhere, kept the approval valid. Links now count by target and content, and a link that leads outside the project makes the approval refused. Approvals of a folder that contains links need to be given again once; others stay valid.
- **Partial coverage is visible** (SH130-02): a command with quotes or shell syntax and no `verify.inputs` shows as `approved, partial coverage`, and doctor warns. It still runs: making `verify.inputs` mandatory would break working setups.
- `/swift-harness:doctor` reads quoted package paths with spaces in the generated `scripts/verify.sh` (SH130-05), and says when a `PACKAGES` list cannot be read without running the script instead of reporting a false failure.
- Component detection in the registry check: a conformance list on the next line is found, declarations inside block comments are not (SH130-07).
- `tests/real-app/contracts.sh <package>` repeats the architecture contracts check on any real SwiftPM package, on a copy (SH130-08). Run on the ~97k-line app of #13: 8 targets, pass, a disallowed edge and a missing target both fail.

## swift-harness 1.3.0 (2026-11-06)

Architecture you can enforce, and the product as a whole. **Upgrading:** in a project whose `docs/COMPONENT_REGISTRY.md` has an entry pointing to a missing file or an undeclared name, the end of a turn that changes code is now blocked until the registry is fixed. Run `/swift-harness:doctor` first to see it; `"registry": {"enabled": false}` turns the check off. Nothing else needs a change: architecture contracts and the product map are opt-in.

- New: architecture contracts for SwiftPM projects ([#13](https://github.com/davidelarocca/swift-harness/issues/13)). `docs/architecture-contracts.json` lists the dependencies each target may have. The end-of-turn check, and the post-edit hook after a `Package.swift` edit, read the real graph with `swift package dump-package` and fail on a dependency the contract does not allow, or a target it does not list, naming the package, target and dependency. They run only while the verify command is approved, since reading a manifest runs it. A contract changed during the session is shown to you at the end of the turn, with the dependencies added and removed. `/swift-harness:doctor` checks the file without running any manifest; `/swift-harness:setup` offers to create it from the current graph.
- New: the component registry is checked ([#7](https://github.com/davidelarocca/swift-harness/issues/7)). At the end of each turn that changes code or the registry, `scripts/registry.sh` reads `docs/COMPONENT_REGISTRY.md` and fails the turn when a File does not exist or does not declare the component's Name, when an ID or name is listed twice, or when a Retired ID is still listed, naming the registry line. It reads Markdown only, so it runs without the verify approval. After an edit in `registry.sources`, Claude is told which views, modifiers and styles in that file the registry does not list, and which entries point to it. `/swift-harness:doctor` shows the result and the components not listed. New config keys `registry.enabled`, `registry.path`, `registry.sources`; the registry template gets an Internal section. **Existing projects:** a registry with a stale entry now blocks the end of a turn until it is fixed (`/swift-harness:doctor` shows it first, `registry.enabled: false` turns the check off); add `registry.sources` to find unlisted components.
- New `/swift-harness:product-map` ([#30](https://github.com/davidelarocca/swift-harness/issues/30)): a read-only map of the product from its code: entities, their pages, every place each one appears, relations, collections the user creates or organizes, and action sets. It lists the gaps with `file:line` evidence and a priority: items you cannot open from where they are shown, related items shown as plain text (or styled as links that do nothing), collections without rename, reorder, delete or undo, actions offered in some places and not others. It writes `docs/PRODUCT_MAP.md` after you approve. On a real ~97k-line app it found the missing cross-links that a generic UX review of the same code did not.
- The product map guides daily work: `setup` adds an empty `docs/PRODUCT_MAP.md` and links it from `CLAUDE.md` and the architecture hub; the UI rule, `feature` and `ui-change` read it before showing an entity in a new place (open it, reach the related entities shown with it, offer its usual actions) and update it in the same change; `ui-reviewer` checks product coherence. Existing projects: run `/swift-harness:product-map`, then add the line to `CLAUDE.md` it suggests.
- `/swift-harness:setup` finds the app's security settings (`*.entitlements`, app `Info.plist`, `PrivacyInfo.xcprivacy`) and proposes them as protected paths, file by file, so Claude asks before relaxing an entitlement to make something work. Existing projects: add those paths to `protectedPaths` in `.claude/swift-harness.json`.
- Smoke suite: a `product` group of 3 scenarios (`tests/smoke/run.sh product`, not in the default run). Showing tasks due today on Home: with the plugin, every row opened the task, the project name opened the project and the shared task menu was used; without it, the project name was plain text. One run each, recorded in `tests/smoke/RESULTS.md`.
- Tests: every skill is named like its folder, every `${CLAUDE_PLUGIN_ROOT}` path a skill cites exists, every docs and rules template is in the setup table, and every doc linked from the templates has one.

## swift-harness 1.2.1 (2026-11-06)

Fixes from an external audit of 1.2.0. No configuration changes needed.

- **Approval coverage** (SH120-01): the verify command is split on spaces, not parsed as shell, so a script named in quotes (`bash "scripts/my verify.sh" fast`) was not covered by the approval, and the status did not say so: editing that script left the command approved. Now `/swift-harness:approve-verify` warns when the command has quotes or shell syntax, and the new `verify.inputs` lists files or folders the approval covers whatever the command looks like. A missing input is shown as missing, and approving again is needed once it appears; a path outside the project is refused. Existing approvals stay valid unless you add `verify.inputs`.
- **Xcode projects with spaces in the name** (SH120-05): the generated `scripts/verify.sh` passed `-project My App.xcodeproj` to xcodebuild as three words. It now keeps the path as one argument. Already generated scripts do not update on their own: copy the `CONTAINER_ARGS` lines from the template, or run `/swift-harness:setup` again.
- **Docs** (SH120-02): 1.2.0 said that unchanged code is verified again once after a plugin update. It is not: the old result stops counting, and the check runs at the end of the next turn that changes build inputs. `/swift-harness:doctor` shows the code as not verified until then. README fixed.
- `/swift-harness:doctor` knows `verify.inputs` and checks that it is a list of paths.
- Smoke suite: a `reuse` group of 6 scenarios for the problem swift-harness exists for, a second copy of an existing UI component ([#19](https://github.com/davidelarocca/swift-harness/issues/19)). The app has a shared pill presenter; Claude is asked for a confirmation on another screen, then for one with an Undo action the pill does not support. Each scenario also runs without the plugin as a baseline. Result: with this model and this small app, Claude reused or extended the pill in every run, with and without swift-harness. The differences were in the registry, previews, tests and cost, recorded in `tests/smoke/RESULTS.md`. Run with `tests/smoke/run.sh reuse`; not part of the default run.

## swift-harness 1.2.0 (2026-11-06)

Trust and onboarding. **Upgrading:** the end-of-turn check runs nothing from the repository until you type `/swift-harness:approve-verify` once in each project (and each worktree). Claude is told at session start, and `/swift-harness:doctor` shows it.

- **Breaking for existing projects:** the end-of-turn check runs the repository's `verify.command` only after you approve it ([#6](https://github.com/davidelarocca/swift-harness/issues/6)). Type `/swift-harness:approve-verify` once per project (and per worktree) after updating. Until then nothing from the repository runs, Claude is told at session start, and you get one warning per code state. The approval is stored in the plugin data folder, outside the repository, and covers the project path, the command and the content of each file it names: change any of them and the check asks again. `/swift-harness:approve-verify revoke` removes it. `lintBlocking` keeps working without the approval, but a clean lint alone is not recorded as a passed verification.
- `/swift-harness:setup` ends by asking you to approve the generated verify command.
- New `/swift-harness:doctor` ([#12](https://github.com/davidelarocca/swift-harness/issues/12)): a read-only diagnosis of the project's setup, one PASS / WARN / FAIL / INFO row per check with the fix. It checks jq, Xcode, the formatter and SwiftLint, unknown or invalid config keys, `{{...}}` placeholders left in generated files, protected paths that do not exist, the verify script (present, executable, scheme or packages set, packages that exist) and its approval, `.swift-format` with swift-format, the SwiftPM layout (for the planned architecture contracts) and the last verification of the current code. It changes no file and creates no state folder.
- A verification result now belongs to the code and to the plugin version ([#18](https://github.com/davidelarocca/swift-harness/issues/18)). Before, a pass recorded by an older version still counted after an update that made the checks stricter. Now unchanged code is verified again once after an update. The project's policy (`lintBlocking`, `verify.command`) was already part of the code state.
- More build inputs count as changes: workspaces (`contents.xcworkspacedata`), and every file under a SwiftPM `Sources/` or `Tests/` folder, so resources outside `Resources/` and test fixtures trigger the check. Xcode per-user state (`xcuserdata`) and `.DS_Store` are ignored.
- SECURITY.md describes what the approval covers and what it does not: files the command reads without naming them, the build itself (Run Script phases, SwiftPM manifests and plugins), and Claude Code's own project hooks. The "never does" guarantee now covers only the plugin's own scripts: an approved verify command runs with your permissions, and even the generated `verify.sh` downloads dependencies and writes SwiftPM and Xcode caches outside the project.
- Smoke suite: 11 scenarios. New: `verify-unapproved`, `approve-verify` and `doctor`.
